# フロントエンドテスト・パターンマトリクス

## 共通条件

| 項目 | 定義 |
| --- | --- |
| 対象画面 | 確定済みの座席予約画面（`SeatReservationPage`） |
| テスト範囲 | 日付・仮ユーザー入力 → 座席表示・選択 → 予約／キャンセル → 結果通知・再取得、およびポーリング |
| 単体テスト | Vitest + React Testing Library。日付処理、APIクライアント、状態管理フックを検証 |
| 画面テスト | Playwright + Chrome。ブラウザ操作と画面表示を検証 |
| Mock | 単体では`fetch`またはAPI関数を置き換える。既存の画面テストでは`/api/`への通信を代替する |
| DB | 単体・API代替の画面テストでは使用しない。実API結合確認のみ専用の検証用PostgreSQLを使用 |
| 基準日 | 日本時間（`Asia/Tokyo`）の当日をDとする。既存自動テストの通常時刻は`2026-10-12T01:00:00Z`（日本時間10時） |
| ユーザーA | `demo-user-1`（画面表示：ユーザー1） |
| ユーザーB | `demo-user-2`（画面表示：ユーザー2） |
| 通常の事前条件 | D、ユーザーA、取得成功、未選択。特記がなければ座席1は空席、座席5はAの予約、座席8はBの予約、残りは空席 |
| 初期座席 | 1〜30。追加・空配列のケースを除き、座席番号の昇順で返す |
| データ分離 | 各テストで時刻・応答・予約データ・モック・タイマーを初期化し、別テストの結果に依存しない |
| 更新間隔 | 前回GETの完了から5秒後に次回取得。リクエスト所要時間を含む固定5秒周期ではない |
| 通信タイムアウト | 10秒。時刻を制御し、実時間での長時間待機を避ける |
| 画面幅 | デスクトップ：1280px、スマートフォン代表：320px |
| 結果の記入 | 未実施／OK／NG／対象外 |

### 補助テストとの対応

補助テストは、対応IDの確認事項の一部を別のテスト層または一連の操作で検証する。対応IDの全確認事項を満たすことを意味せず、補助テストの成功だけでマトリクスの結果をOKとしない。「このテストでは確認しない内容」は当該補助テストの検証範囲を示し、テスト全体の不足を意味しない。既存のID付きテストと合わせて確認する。

## 記入・実装ルール

- 「／」で並べた日付・操作・応答は、それぞれ別ケースまたはパラメータ化テストとして実行する。一部だけの成功で行全体をOKにしない。
- 画面から送られるHTTPとAPIクライアント単体の検証を区別する。フックでAPI関数をモックしたテストだけではヘッダー・JSON本文の送信は確認できない。
- HTTP 201／204を返すモックの成功は、実バックエンドのトランザクションやDB制約の成功を意味しない。実API結合確認の結果を別に残す。
- 競合・応答逆転は応答を保留して順序を制御する。単なる待ち時間に頼って偶然の競合を期待しない。
- ポーリングは現在の日付・ユーザー、開始間隔、選択維持／解除、最終確認時刻を確認する。GETの件数だけで合格にしない。
- React StrictModeで初期GETが中断・再発行されることは許容する。重複防止の判定は書き込みと同一取得世代の定期GETを対象にする。
- ボタン無効の見た目だけでなく、実際に追加のPOST・DELETEが送られないことも確認する。
- 書き込みの通信切断・タイムアウトでは、サーバー側で完了している可能性を考慮し、成功・失敗の断定や自動再送がないことを確認する。
- スクリーンショットを保存しただけでは外観検証の合格としない。目視照合または画像比較を実施する。
- テストを追加・修正する際はケースIDをテスト名または本書の対応表に残す。実行日、対象コミット、実行環境、失敗内容も結果と併記する。
