# ADR-005: 予約・キャンセルの競合制御とTransaction境界

- **日付**: 2026-10-15
- **ステータス**: Accepted
- **対象**: Phase 2 / Transaction・Concurrency

## 背景

- 同時予約・キャンセル時の競合を考慮する必要がある。
- Phase 1ではUNIQUE制約とService単位のTransactionを採用している。
- 現行方式で整合性が維持されるか検証した。

## 決定

- 二重予約は`UNIQUE (reservation_date, seat_number)`で防止し、対象制約違反は409を返す。
- Service単位の`@Transactional`と、DB設定の`READ COMMITTED`を継続する。
- キャンセルは明示DELETEの削除件数で判定し、1件なら204、0件なら専用例外を共通例外ハンドラーで404へ変換する。
- Controllerの存在・所有者・過去日確認は維持し、追加の楽観ロック・悲観ロックは導入しない。

## 理由

- **UNIQUE制約（採用）**：存在しない予約への競合INSERTにも適用でき、Transactionと組み合わせて一意性とcommit / rollbackを保証できる。
- **削除件数判定（採用）**：同時キャンセルで発生していた500や、削除対象が消えた後の二重204を防ぎ、後続を404として扱える。
- **楽観ロック（不採用）**：競合INSERTには別途UNIQUE制約が必要で、現状の取消競合は削除件数で判定できる。
- **悲観ロック（不採用）**：現行要件を満たすために追加する必要がなく、ロック対象によっては別日付・別座席の操作まで待機させる可能性がある。

競合・rollback・異なるリソースの独立した進行は結合テストで確認した。検証範囲と結果は[Transaction / Concurrencyテスト定義](../testing/transaction-concurrency-test-matrix.md)に記録する。

## 影響・今後の拡張

- DELETEは明示クエリ実行時に発行されるが、rollbackによる取消は維持する。存在しないIDでのService直接呼び出しも例外となる。
- 一括DELETEはEntityの削除コールバックや管理中Entityの状態更新を行わない。関連Entity・削除時処理を追加する場合は再検討する。
- 所有者・予約日の更新機能を追加する場合は、Transaction外の確認と削除の間の競合を考慮し、境界・削除条件・ロック方式を見直す。
