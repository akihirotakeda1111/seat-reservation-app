# ADR-006: 認証アーキテクチャとユーザー管理方針の選定

- **日付**: 2026-10-16
- **ステータス**: Accepted
- **対象**: Phase 3 / Authentication・Authorization

## 背景

座席予約システムに認証認可を導入するにあたり、SPAによるJWT認証とBFFによるセッション認証を比較した。

本Phaseでは、Cognitoによる認証、Spring SecurityによるJWT検証、ロール別認可、予約所有者に基づく認可の実践を目的とする。

また、予約業務で必要なユーザー情報は識別子のみであるため、アプリケーション側でユーザー情報を管理する必要性についても検討した。

## 決定

**SPA + JWT認証を採用し、ユーザー管理はCognitoに集約する。**

- ReactがCognito Managed LoginとAuthorization Code Flow with PKCEを利用して認証する。
- ReactがAccess Tokenを管理し、Spring Boot APIへBearer Tokenとして送信する。
- Spring SecurityがJWTを検証し、ロール別のアクセス制御を行う。
- Spring BootのServiceが予約所有者に基づく認可を行う。
- Spring Boot APIはステートレスに構成する。
- Cognito Groupsの`ADMINS`で管理者権限を管理し、その他の認証済みユーザーは一般ユーザーとして扱う。
- アプリケーションDBに`users`テーブルは作成しない。
- 予約所有者はJWTの`sub`で識別し、`reservations.user_id`に保存する。
- CognitoとアプリケーションDB間でユーザー情報の同期は行わない。

## 理由

### 認証アーキテクチャ

- **SPA + JWT（採用）**：ブラウザ側でトークン管理が必要になるが、Spring SecurityによるJWT検証とステートレスなAPI認証認可を直接実践できる。
- **BFF + セッション（不採用）**：認証情報をサーバー側へ集約できるが、BFFとセッション管理が必要となり、実装範囲が拡大する。

今回は認証認可の学習を優先し、追加コンポーネントを必要としないSPA + JWTを採用する。

### ユーザー管理

- **アプリケーションDBで管理（不採用）**：ユーザー属性を独自管理できるが、ユーザーテーブルとCognitoとの情報同期が必要になる。
- **Cognitoに集約（採用）**：予約業務に必要な識別子をJWTから取得でき、ユーザー情報の二重管理を避けられる。

アプリケーション固有のユーザー属性を保持する要件がないため、Cognitoの`sub`を予約所有者の識別子として利用する。

## 影響・今後の拡張

- SPAでAccess Tokenを扱うため、XSS対策、トークンの安全な保持、有効期限管理が必要となる。
- JWTに含まれるGroup情報は発行済みトークンに固定されるため、権限変更が即時反映されることは保証しない。
- CognitoのUser Poolにユーザー識別を依存する。User Pool再作成時は`sub`が変わるため、既存予約との関連を引き継ぐには移行処理が必要となる。
- ユーザー削除時の予約データの扱いや、アプリケーション固有のプロフィール管理は今回の対象外とする。
- 認証情報のサーバー側集約が必要になった場合は、BFF導入を再検討する。その際はセッション管理、Cookie、CSRF対策を設計対象とする。
- ユーザー固有の情報を永続化する要件が生じた場合は、ユーザーテーブルの追加を検討する。
