# ADR-007: CloudFront VPC Originsの採用

- **日付**: 2026-10-20
- **ステータス**: Accepted
- **対象**: Phase 4 / AWS Infrastructure

## 背景

座席予約システムをAWSへデプロイするにあたり、CloudFrontを公開入口とし、Spring Boot APIをECS/Fargateで稼働させる。

Backendへの通信経路として、Public ALBをCloudFrontのオリジンとする方式と、CloudFront VPC Originsを使用してInternal ALBをオリジンとする方式を比較した。

## 決定

**CloudFront VPC Originsを採用する。**

ネットワーク構成は以下とする。

```text
Browser
    |
    v
CloudFront（公開）
    |
    +-- S3（非公開 / OAC）
    |     React静的ファイル
    |
    +-- VPC Origins
            |
            v
        Internal ALB
            |
            v
        ECS/Fargate
            |
            v
        RDS PostgreSQL
```

- ALB、ECS、RDSをPrivate Subnetに配置する。
- ALBへのアクセスはCloudFront VPC Originsに限定する。
- ECSへのアクセスはALBに限定する。
- RDSへのアクセスはECSに限定する。
- 認証・認可は引き続きCognitoとSpring Securityで実施する。

**追記（2026-10-27）：実装時の具体化**

- 採用構成は維持し、CloudFront → ALBをHTTPS:443、ALB → ECSをHTTP:8080で実装した。
- DNS・ACMは手動管理とし、Terraformには公開／Origin用FQDNと既存証明書ARNを渡す。

## 理由

### 公開範囲の最小化

ALBをインターネットへ公開せず、CloudFrontを唯一の公開入口とする。これにより、CloudFrontを迂回したBackendへの直接アクセスを防ぐ。

### セキュリティ境界の明確化

CloudFront、ALB、ECS、RDSの各レイヤーで通信元を制限する。アプリケーションの認証認可とは独立して、ネットワークレベルのアクセス制御を実施する。

### アクセス制御の簡素化

Public ALBで必要となるCloudFront送信元の制限や専用ヘッダー検証への依存を減らす。

### 代替案との比較

- **CloudFront VPC Origins + Internal ALB（採用）**：ALBをインターネットへ公開せず、公開範囲を最小化できる。
- **Public ALB + CloudFront（不採用）**：Security Groupと専用ヘッダー検証によってアクセスを制限でき、システム要件を満たせる。構築とデバッグが比較的容易という利点があるが、ALB自体はインターネット向けとなる。

今回は公開範囲を最小化できるVPC Originsを優先する。

## 影響・今後の拡張

以下は当初想定した影響と検討事項。

- VPC Originリソースの追加によりTerraformの構成・依存関係が増える。
- Internal ALBに外部から直接アクセスできないため、障害調査はCloudFrontやALBのログ等を利用する。
- CloudFront VPC Origins自体に追加料金は発生しない。
- ECSからECR、CloudWatch Logs、Cognitoの公開鍵取得先などへの外向き通信は別途設計が必要となる。
- GitHub Actionsによるビルド・テスト・デプロイ方式は基本的に変更しない。
- デプロイ後のAPI疎通確認はCloudFront経由で実施する。

**追記（2026-10-27）：実装による具体化**

- 外向き通信はNAT Gateway 1台を経由する構成で実装した。
- GitHub Actionsによる自動化の方針は維持するが、Workflow・OIDC Roleは未実装。現在は手動デプロイを行う。
- ECS初回起動・ロールバック・State管理の詳細は[AWS設計](../system-design/aws-architecture.md)と[CI/CD設計](../system-design/cicd-design.md)、操作は[Terraform README](../../terraform/README.md)を参照する。

### 実装時の確認事項

当初の確認事項を残し、実装状況と実環境での確認状況を併記する。

| 当初の確認事項 | 2026-10-27時点 |
| --- | --- |
| VPC Originsの前提条件（Internet Gateway、Private Subnet、ENI用IPアドレス）を満たす | IGW・Private SubnetをTerraformで定義。ENI用IPの空きは構築時の確認対象 |
| CloudFront管理Security GroupでALBへの着信を制限する | 当該Security Groupから443番ポートへの着信を許可する構成を実装 |
| `/api/*`のキャッシュを無効化し、Authorization・クエリ・必要なHTTPメソッドを転送する | 実装済み。`/api`も追加し、SPA書き換えはS3側に限定 |
| CloudFront → ALBのHTTP／HTTPSを決定する | Phase 4のHTTPS方針を具体化し、HTTPS:443で実装 |
| CloudFront経由のAPI疎通と、ALBへの外部直接アクセス不可を確認する | 公開URLでの表示・ログイン・業務操作は利用者による確認済み。ALBの非公開構成は実装済みだが、外部からの到達性検証は未確認 |

### 対象外

以下は本ADRでは決定せず、Phase 4の関連設計で別途判断する。

- ECSの外向き通信方式（NAT Gateway / VPC Endpoint）
- CI/CDでのCognito実環境E2Eテストの自動化
- WAFや追加のDDoS対策の導入

**追記（2026-10-27）：** 外向き通信方式は[AWS設計](../system-design/aws-architecture.md)でNAT Gatewayに決定した。VPC Endpointによる最適化、実認証E2EのCI化、WAFは引き続き追加学習対象とする。
